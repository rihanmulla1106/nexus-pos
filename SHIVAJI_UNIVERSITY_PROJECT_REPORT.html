CHAPTER 1: SYSTEM ANALYSIS

1.1 Background of the Problem

In physical retail stores (such as grocery supermarkets, electrical shops, clothing boutiques, and independent retail outlets in regional towns like Jath and across Maharashtra), billing and inventory tracking form the core daily operations. Historically, storekeepers relied on handwritten ledger books or basic disconnected desktop spreadsheets.

While modern cloud-based Software-as-a-Service (SaaS) POS platforms have emerged, they require uninterrupted high-speed internet connections and recurring monthly subscriptions. In semi-urban and rural retail hubs, internet connectivity frequently fluctuates or drops. When a cloud POS disconnects, the cashier cannot scan barcodes, generate bills, or calculate balances, leading to long customer queues, transaction abandonment, and severe financial losses.

1.2 Existing System and Its Limitations

The existing systems used by small merchants fall into two categories:

  1. Manual Paper Ledgers / Excel Sheets:
    • Prone to manual mathematical errors in tax, discount, and change calculations.
    • No automated stock decrement upon billing; inventory counts require time-consuming manual audits.
    • Zero customer history tracking or loyalty rewards.
  2. Cloud-Based POS Systems (e.g., Shopify POS, Square):
    • Internet Vulnerability: Complete halt of retail operations during network downtime.
    • Prohibitive Recurring Costs: Recurring monthly charges ($89+/month) plus transaction percentage fees.
    • Data Privacy Risks: Store financial records and customer phone numbers are hosted on remote third-party cloud servers.

1.3 Objective of the Project

  • To build a 100% offline-first desktop application with zero internet reliance.
  • To provide sub-10 millisecond billing response times using local SQLite embedded storage.
  • To enforce Role-Based Access Control (RBAC) separating Admin settings from Staff checkout actions.
  • To protect user credentials using memory-hard cryptographic password hashing (scrypt).
  • To integrate hardware USB barcode scanners via keyboard emulation event listeners.
  • To support dual-format invoice compilation: standard A4 documents and 80mm POS thermal receipt rolls.
  • To automate inventory decrement on checkout and restock restoration on refund.

1.4 Scope of the Project

The scope of Nexus POS covers single-terminal physical retail establishments, including department stores, pharmacies, hardware outlets, and apparel shops. It encompasses product catalog management, barcode-driven billing, customer CRM with loyalty points, daily expense auditing, graphical revenue reporting, and local database disaster backup.

CHAPTER 2: SYSTEM STUDY / PROPOSED SYSTEM

2.1 Software Development Model

The project was developed using the Agile Iterative Prototyping Model. This software engineering methodology allowed rapid phase-by-phase development, continuous refinement, and rigorous verification:

  • Phase 1 (Requirements & Architecture): Decoupled Electron multi-process design and schema creation.
  • Phase 2 (Core Inventory & POS Terminal): Rapid UI wireframing with React and Vite.
  • Phase 3 (Billing & Dual PDF Engine): Integrated `jsPDF` for A4 invoices and 80mm thermal rolls.
  • Phase 4 (Enterprise Security & CRM): Implemented `scrypt` cryptographic hashing and customer loyalty points.
  • Phase 5 (Financial Auditing & Expenses): Built daily expense tracking and net profit math.
  • Phase 6 (Automated QA & Packaging): Wrote automated Vitest unit test suites and built Windows `.exe` installers.

2.2 Feasibility Study

A three-dimensional feasibility analysis was conducted:

Feasibility Dimension Evaluation & Findings
Technical Feasibility Built on Electron v39.x, React 19, and SQLite3. These technologies run natively on standard commodity PC hardware without needing expensive server configurations or high-end graphics processing units.
Operational Feasibility The UI is built with high-contrast, modern glassmorphism dark aesthetics and intuitive ergonomics. Cashiers with basic computer literacy can scan barcodes and issue receipts with zero training.
Economic Feasibility The software uses 100% open-source libraries and embedded SQLite. It imposes ₹0 recurring monthly server costs, zero cloud subscription fees, and eliminates recurring licensing charges.

CHAPTER 4: SYSTEM DESIGN

4.1 System Architecture Diagram / DFD

Nexus POS implements Electron's multi-process architecture. The Main Process runs in Node.js and executes privileged disk I/O and SQLite operations. The Renderer Process renders the React 19 UI inside a secure Chromium sandbox. Communication is strictly routed through an asynchronous IPC (Inter-Process Communication) bridge.

DFD Level 0: Context Diagram

External Entities: Administrator, Cashier/Staff, Customer.
Inputs to System: Credentials, Barcode scans, Cart items, Tendered payments, Expense records, Settings.
Outputs from System: Printed A4 / Thermal bills, Change due, Stock availability alerts, Visual revenue reports, SQLite backup file.

DFD Level 1: Process Decomposition

• Process 1.0 (Auth & RBAC): Queries Data Store D1 (users) via scrypt hash comparison.
• Process 2.0 (Inventory Control): Reads/Writes Data Store D2 (products).
• Process 3.0 (POS & Billing): Queries D2, writes transaction records to D3 (invoices & invoice_items), and fetches tax settings from D6.
• Process 4.0 (CRM & Loyalty): Writes accrued points to Data Store D4 (customers).
• Process 5.0 (Expense Logging): Writes daily cash outflows to Data Store D5 (expenses).
• Process 6.0 (Executive Analytics): Aggregates D2, D3, and D5 to compute net business performance.

DFD Level 2: Point of Sale & Billing Sub-Process

• 3.1 Input SKU: Intercepts barcode keystroke sequence.
• 3.2 Validate Stock: Checks available stock > 0 in SQLite products table.
• 3.3 Cart Math: Computes Subtotal, Tax Percentage, and Total tendered.
• 3.4 Split Tender: Calculates balance due or change tendered for Cash, Card, and UPI.
• 3.5 Persistence & Restock: Commits invoice, decrements stock, awards CRM loyalty points.

4.2 Database Design (ER Diagram)

The database schema is fully normalized into seven relational tables in SQLite:

Table Name Primary Key Foreign Key(s) Attributes & Description
`users` id None username (UNIQUE), password (scrypt hash), role (Admin/Staff)
`products` id None name, sku (UNIQUE), price, stock
`invoices` id None customer_name, customer_phone, date, total, amount_paid, balance_due, payment_method, status
`invoice_items` id invoice_id, product_id quantity, price (Snapshot at time of sale)
`customers` id None name, phone (UNIQUE), points
`expenses` id None description, amount, date
`settings` key None value (Store name, currency symbol, tax percentage)

CHAPTER 5: IMPLEMENTATION

5.1 Module-wise Screenshots of Input & Output Design

Provides a secure dark-mode portal. Authenticates users using cryptographic hash comparisons. Restricts administrative navigation links if the user role is 'Staff'.

Displays high-level KPI cards (Total Sales, Total Products, Low Stock Count, Today's Profit) and a clean weekly revenue performance graph.

5.2 Reports

Nexus POS dynamically compiles invoices on the client using jsPDF and jsPDF-AutoTable. Two layout formats are available:

  1. Standard A4 Tax Invoice: Clean full-page document including store metadata, invoice numbers, customer phone numbers, itemized tables, subtotal, tax breakdown, and signature blocks.
  2. 80mm Thermal Receipt: Formatted specifically for POS thermal rolls with condensed typography, dashed dividers, and receipt footers.

CHAPTER 7: CONCLUSION & FUTURE SCOPE

7.1 Summary of Work

Nexus POS demonstrates the viability of modern desktop retail architectures. By integrating React 19 and Vite with Electron and SQLite, the platform provides the visual fluidity of modern web applications while delivering the speed, data privacy, and zero-latency reliability of local embedded databases. It satisfies all functional requirements set forth by physical retail merchants.

7.2 Limitations

  • Single-Terminal Scope: Operates locally on one PC; cannot yet sync across multiple cash registers simultaneously in large supermarkets.
  • Direct Hardware Serial Hooks: ESC/POS cash drawer triggers currently rely on standard printer drivers rather than raw serial communication.

7.3 Learning Outcomes

  • Mastered Electron's decoupled multi-process architecture and secure IPC bridges using contextBridge.
  • Gained deep practical expertise in salted cryptographic key derivation algorithms (scrypt) and timing-safe equality checks.
  • Implemented hardware keyboard event interception in React for rapid barcode input.
  • Learned automated frontend unit testing using Vitest, JSDOM, and React Testing Library.

7.4 Possible Enhancements

  • LAN Multi-Counter Sync: Adding local WebSocket synchronization to connect multiple cashier terminals to a master register node.
  • Hardware ESC/POS Drivers: Direct binary communication to trigger automatic physical cash drawer kickouts and thermal paper cutters.
  • Optional Encrypted Cloud Mirroring: Scheduled end-to-end encrypted backup uploads to Google Drive or AWS S3.
