CHAPTER 1: INTRODUCTION

1.1 Background & Motivation

In contemporary retail environments, point-of-sale operations are the backbone of day-to-day business continuity. While modern Software-as-a-Service (SaaS) cloud POS solutions (such as Shopify POS, Square, and Lightspeed) offer centralized dashboards, they introduce severe systemic dependencies: required recurring monthly fees, privacy vulnerability of customer records, and critical vulnerability to internet outages. For small-to-medium enterprises (SMEs) and independent retail merchants, an offline-first desktop architecture offers 100% operational uptime, zero recurring subscription fees, and complete local data privacy.

1.2 Problem Statement

Small businesses frequently encounter lost revenue, cashier delays, and queue build-ups during internet disconnects when using cloud-reliant systems. Furthermore, multi-tier pricing models squeeze small retail margins. Nexus POS was engineered to provide an enterprise-grade desktop point of sale system capable of running fully detached from external servers while retaining modern ergonomics, dynamic stock management, and cryptographic user security.

1.3 Project Objectives

  • Implement a zero-downtime, local-first transaction terminal using SQLite.
  • Enforce Role-Based Access Control (RBAC) separating administrative actions from billing operations.
  • Protect user credentials using modern salt-based scrypt cryptographic key derivation.
  • Integrate hardware barcode scanning via event listeners without specialized SDKs.
  • Generate dual-mode printable receipts (Standard A4 and 80mm thermal rolls).
  • Automate unit testing utilizing Vitest and React Testing Library.

CHAPTER 3: SYSTEM DESIGN & ARCHITECTURE

3.1 Multi-Process Architecture

Nexus POS implements Electron's security-first multi-process architecture. The Main Process runs in Node.js and retains privileged access to operating system APIs, file dialogs, and SQLite disk operations. The Renderer Process runs the React-based frontend inside an isolated Chromium sandbox. Communication between both layers is achieved through an explicit, asynchronous Inter-Process Communication (IPC) bridge (`ipcMain.handle` and `ipcRenderer.invoke`) exposed safely via `contextBridge`.

3.2 Database Schema Overview

The local relational database (`inventory_billing.db`) is structured into seven distinct tables:

  • `users`: Stores administrative and staff credentials with salted `scrypt` hashes.
  • `products`: Manages catalog SKUs, names, pricing, and stock levels.
  • `invoices`: Records sales transactions, customer links, payment modes, amounts paid, and dues.
  • `invoice_items`: Junction table storing line-item snapshot prices and quantities per invoice.
  • `customers`: Maintains client registry, phone numbers, and accrued loyalty points.
  • `expenses`: Logs daily operational expenditures for net profit calculations.
  • `settings`: Persists store metadata, tax percentages, and local currency symbols.

CHAPTER 4: IMPLEMENTATION & KEY MODULES

4.1 Cryptographic Password Security

Unlike naive POS systems that store credentials in plain text or outdated MD5 hashes, Nexus POS employs salted cryptographic key derivation via the scrypt algorithm. A cryptographically strong 16-byte random salt is generated for each user. Passwords are saved as <salt>:<derivedKey>. Authentication executes timing-safe comparisons to prevent side-channel timing attacks:

const crypto = require('crypto') const salt = crypto.randomBytes(16).toString('hex') const key = crypto.scryptSync(password, salt, 64).toString('hex') const hash = `${salt}:${key}` // Stored securely into SQLite 'users' table

4.2 Point of Sale Terminal & Barcode Scanner Integration

The POS checkout module features a hardware-agnostic barcode scanner listener. USB barcode readers emulate high-speed keyboard input terminating with an Enter keystroke. The React application listens for rapid keystrokes occurring within a 500ms window; when a scan sequence finishes with carriage return, the matching SKU is immediately located in memory and added to the cart without requiring manual cursor focus.

4.3 Dual-Format Invoice Generation

Receipts are compiled client-side using `jsPDF`. The system supports two distinct layout engines:

  1. Standard A4 PDF: Suitable for formal business-to-business invoicing and office printers.
  2. 80mm Thermal Receipt (POS Roll): Formats the document with narrow margins, condensed typography, and variable height suited for standard point-of-sale thermal receipt printers.

CHAPTER 6: CONCLUSION & FUTURE SCOPE

6.1 Conclusion

Nexus POS successfully achieves all of its architectural and functional goals. It bridges the gap between modern, responsive web technologies (React 19) and rock-solid offline desktop systems (Electron and SQLite). By providing zero-latency processing, split-payment tracking, automated stock safety routines, and cryptographic user security without recurring SaaS fees, it stands as an efficient and practical commercial-ready solution for physical retail stores.

6.2 Future Enhancements

  • Local Area Network (LAN) Synchronization: Enabling multi-terminal support across a single store using local WebSocket broadcasting or PostgreSQL replication.
  • Direct Thermal Device Commands (ESC/POS): Sending raw ESC/POS binary instructions to trigger automatic cash-drawer kickout and paper cutters.
  • Cloud Backup Sync (Hybrid Mode): Providing optional end-to-end encrypted daily cloud snapshots for disaster recovery.
